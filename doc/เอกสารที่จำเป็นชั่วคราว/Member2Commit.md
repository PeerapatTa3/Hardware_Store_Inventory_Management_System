### ทำไมจึงเพิ่ม และทำงานอย่างไร
การกดรับสินค้าเกี่ยวข้องกับข้อมูลหลายส่วน ได้แก่ ยอดคงเหลือ, ประวัติการเคลื่อนไหว และสถานะใบสั่งซื้อ หากอัปเดตเพียงบางส่วนจะทำให้ข้อมูลขัดแย้งกัน Receive จึงครอบทุกการเปลี่ยนแปลงใน transaction เดียว หากเพิ่ม stock หรือบันทึก movement ของรายการใดไม่สำเร็จ การเปลี่ยนแปลงทั้งหมดของใบนี้จะ rollback กลับ

### สิ่งที่โปรเจกต์มีเพิ่มและประโยชน์
- เชื่อมขั้นตอนรับของกับยอดคงคลังและประวัติ `IN`
- ใช้สถานะ `COMPLETED` เป็นหลักฐานว่ารับสินค้าแล้ว
- ป้องกันการเพิ่ม stock ซ้ำจากการรับใบเดิมซ้ำ
- ลดโอกาสที่ Inventory, Stock Movement และ Purchase status จะไม่ตรงกัน

### มุมมองผู้ใช้ที่ไม่ใช่ Developer
เมื่อเจ้าหน้าที่รับสินค้า ระบบจะเพิ่มจำนวนสินค้าทุกบรรทัดเข้าคลังและบันทึกว่าเข้ามาจากใบสั่งซื้อใด หากมีปัญหากับรายการใดรายการหนึ่ง จะไม่ทิ้งข้อมูลรับสินค้าไว้เพียงบางส่วน และใบสั่งซื้อที่รับเสร็จแล้วจะรับซ้ำไม่ได้

**ผลทดสอบหลังงานนี้:** 42 tests ผ่าน รวมการทดสอบ receive สำเร็จ, ป้องกันรับซ้ำ และ rollback

## ขอบเขตที่ยังไม่รวมใน commit เหล่านี้

- Purchase REST Controller ยังไม่ถูกเพิ่ม ดังนั้น endpoint ที่ระบุใน API documentation ยังไม่พร้อมให้ client เรียกใช้งาน
- ยังไม่มีหน้าจอ Frontend สำหรับ Purchase หรือ Inventory
- งานรับสินค้าในปัจจุบันมี service และ persistence tests รองรับ แต่ยังต้องเพิ่ม Controller tests เมื่อมี REST API
